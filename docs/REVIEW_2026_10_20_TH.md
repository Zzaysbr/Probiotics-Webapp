### 2. สูง: Admin บันทึกสต็อกเก่าทับการจองสินค้าที่เกิดขึ้นแล้ว

- จุดหลัก: `backend/controllers/productController.js:54–58`; หน้า Admin คัดลอกข้อมูลทั้งแถวเข้า form ที่ `frontend/src/views/AdminView.vue:40–60`
- ทดลองจริง: เปิดข้อมูลสินค้าที่สต็อก 50 → ลูกค้าสั่ง 1 ชิ้น สต็อกเหลือ 49 → Admin บันทึกฟอร์มเก่าโดยแก้เฉพาะข้อความสินค้า → API ตอบ 200 และสต็อกกลับเป็น 50
- ผลกระทบ: สินค้าที่ถูกจองแล้วกลับมาถูกนับว่าพร้อมขาย อาจรับคำสั่งซื้อเกินสินค้าที่มี แม้เส้นทาง checkout จะล็อกแถวอย่างถูกต้อง
- ควรแยกการแก้รายละเอียดออกจากการปรับสต็อก ใช้การเพิ่ม/ลดจำนวนแบบ atomic พร้อมประวัติการปรับ หรือใช้ version/updated_at ตรวจข้อมูลเก่าและตอบ 409 ให้โหลดใหม่ การเพิ่ม transaction โดยยังเขียนค่าเก่าแบบเดิมอย่างเดียวไม่แก้สาเหตุนี้
- ควรเพิ่ม regression test ลำดับ Admin เปิดฟอร์ม → ลูกค้าซื้อ → Admin บันทึก และตรวจว่าการคืนสต็อกจากการยกเลิกไม่สูญหายด้วย

### 3. กลาง: ราคาที่ลูกค้ายืนยันในตะกร้าอาจไม่ตรงกับออร์เดอร์ที่ถูกสร้าง

- ตะกร้าเก็บราคา/สต็อกเป็น snapshot ใน localStorage: `frontend/src/services/cart.js:25–39`
- ยอดในหน้าตะกร้าคิดจาก snapshot: `frontend/src/views/CartView.vue:16–22` ขณะที่ backend ใช้ราคาปัจจุบัน: `backend/routes/shopRoutes.js:122`
- ทดลองจริง: ราคาที่ลูกค้าเก็บในตะกร้า 590 บาท → Admin ปรับเป็น 600 บาท → checkout ตอบ 201 สร้างออร์เดอร์ 600 บาททันที โดยไม่มีขั้นตอนยืนยันราคาใหม่
- backend ใช้ราคาจริงเพื่อป้องกันการปลอมยอดนั้นถูกต้อง แต่ควรโหลดราคา/สถานะ/สต็อกล่าสุดก่อนยืนยัน และเมื่อราคาเปลี่ยนให้ผู้ใช้เห็นยอดใหม่และกดยืนยันอีกครั้ง โดย server ต้องตรวจซ้ำตอนสร้างออร์เดอร์เสมอ
- `CartView.vue:91` ใช้ stock_qty เก่าเป็น max ด้วย หากร้านเติมสต็อกภายหลัง ผู้ใช้อาจเลือกจำนวนตามสต็อกล่าสุดไม่ได้จนลบแล้วเพิ่มสินค้าใหม่ ควร refresh ตะกร้าและแจ้งรายการที่เปลี่ยน/เลิกขายอย่างชัดเจน

### 4. กลาง: Username ชนกับ email ของบัญชีอื่น ทำให้ล็อกอินผิดเส้นทาง

- `backend/controllers/authController.js:23` รับ username เป็นข้อความทั่วไป ส่วน login ที่บรรทัด 43 ใช้ `WHERE username=? OR email=?` แล้วหยิบเพียงแถวแรก
- UNIQUE ของ username และ email แยกกัน ไม่ป้องกันการชนข้ามคอลัมน์
- ทดลองจริง: สมัคร username เป็นอีเมลของบัญชีสาธิตอื่นสำเร็จ (201) → ล็อกอินด้วย username/รหัสผ่านใหม่ได้ 401 → ล็อกอินด้วยอีเมลของบัญชีใหม่นั้นได้ 200
- ไม่พบการข้ามรหัสผ่านจากกรณีนี้ แต่เกิดความกำกวมในการเลือกบัญชีและสมาชิกใช้งานชื่อที่เพิ่งสมัครไม่ได้
- ควรกำหนดรูปแบบ username ให้แยกจากอีเมล เช่น ไม่อนุญาต @ พร้อมตรวจบัญชีเดิมที่ชน หรือกำหนดกติกาค้นหาที่แน่นอนและป้องกันการชนทั้งตอนสมัครและเปลี่ยนอีเมลในอนาคต

## สิ่งที่ทำได้ดี

- ตรวจ JWT และ role ฝั่ง backend ทุกเส้นทางที่จำกัดสิทธิ์ สมัครสมาชิกไม่ยอมรับ role admin จาก client
- ใช้ parameterized queries กับค่าที่ผู้ใช้ส่ง และตรวจรูปแบบ/ขนาดข้อมูลก่อนเขียนฐานข้อมูล
- ราคาจริงและชื่อสินค้าสำหรับประวัติออร์เดอร์มาจาก DB ไม่เชื่อราคาจาก client
- ใช้ transaction, row lock, idempotency key และลำดับล็อกสินค้าในการ checkout; กรณีแย่งชิ้นสุดท้ายและยกเลิกซ้ำผ่านชุดทดสอบ
- หลักฐานชำระไม่เปิดเป็น public static และตรวจเจ้าของออร์เดอร์ก่อนดาวน์โหลด
- ไม่รวม pending payments ในยอดขาย อนุมัติซ้ำถูกปฏิเสธ และคืนให้แจ้งใหม่เมื่อหลักฐานไม่ผ่าน
- Reset token เก็บแบบ hash ใช้ครั้งเดียว มีอายุ และเปลี่ยนรหัสผ่านแล้ว JWT เดิมถูกยกเลิก

## ข้อเสนอเพื่อให้เว็บสมบูรณ์ขึ้น (เป็นส่วนเพิ่ม ไม่ใช่ข้อบังคับทั้งหมดในโจทย์)

1. **ออร์เดอร์หมดอายุ:** ปัจจุบันหักสต็อกตั้งแต่สั่งซื้อและคืนเมื่อยกเลิก ยังไม่พบงานอัตโนมัติหมดอายุออร์เดอร์ที่ไม่ชำระ ควรมีเวลาชำระและคืนสต็อกแบบไม่คืนซ้ำ มิฉะนั้นคำสั่งซื้อที่ถูกทิ้งจะกันสินค้าค้างไว้
2. **จัดส่ง:** SQL มี tracking_no แต่ยังไม่มี flow หน้า Admin/API สำหรับกรอกเลขพัสดุและสถานะจัดส่ง ควรเพิ่มรายการรอจัดส่ง กรอกเลขพัสดุ และแสดงให้ลูกค้าดูได้ หากต้องการให้เป็นร้านค้าครบวงจร
3. **รายละเอียดสินค้า:** เพิ่มข้อมูลขนาดบรรจุ วิธีใช้ วิธีเก็บ คำแนะนำ และรูปที่ตรงสินค้า ภาพ CSS fallback ปัจจุบันใช้ข้อความตาม variant ไม่ได้มาจากรายละเอียดสินค้าโดยตรง ควรหลีกเลี่ยงภาพชื่อ/จำนวนบรรจุไม่ตรงสินค้าเมื่อเพิ่มชนิดใหม่
4. **รูปสินค้าจาก SQL เดิม:** dump ใช้ path `uploads/products/...` แต่ ProductsView รองรับภาพเฉพาะ URL http/https จึงแสดง fallback แทน และหน้า Admin จะทำ path เดิมเป็นค่าว่างเมื่อแก้สินค้า ควรกำหนดนโยบาย path/URL ให้ตรงกันและรักษาค่าเดิมเมื่อไม่ได้แก้รูป
5. **ข้อมูลจำนวนมาก:** รายการสินค้า ออร์เดอร์ และ payments โหลดทั้งหมด ยังไม่มี pagination ควรเพิ่มเมื่อข้อมูลโตขึ้น
6. **การสาธิต reset อีเมล:** ใช้อีเมลที่กลุ่มเข้าถึงได้ทดสอบรับลิงก์ เปิดลิงก์ ตั้งรหัสใหม่ และล็อกอินจริงให้ครบก่อนนำเสนอ ผล mock ไม่รับรองการส่งถึง inbox
7. **ฐานข้อมูล/เอกสาร:** ใน SQL แนบ CREATE TABLE ของ products/order_items ไม่ระบุ ENGINE/CHARSET และไม่มี CHECK สำหรับราคา/จำนวน ควรกำหนด InnoDB/utf8mb4 ชัดเจนและเพิ่มข้อจำกัดตามกติกาข้อมูลเพื่อลดการพึ่งค่า default ของเครื่องนำเข้า (การทดสอบรอบนี้สร้าง DB เป็น utf8mb4 ก่อน)
8. **ทำซ้ำได้:** package.json frontend ใช้ `vue: rc` และ overrides หลายรายการเป็น rc ควรเลือกเวอร์ชันที่ทดสอบแล้วและเก็บ lockfile ให้ตรงกัน เพื่อให้การติดตั้งครั้งต่อไปตรวจสอบย้อนกลับได้
